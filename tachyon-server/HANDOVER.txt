1. WHAT YOU ARE FIXING
--------------------------------------------------------------------------------
Flux Rec is a private Rec Room revival. The 2026 Rec Room client
(build 20260323.14) does NOT use Photon for rooms — its room transport is
"Tachyon": a forked Unity Netcode (NGO) over LiteNetLib. This .NET 8 server
(src/) is the Tachyon endpoint: connection approval (RSA->AES "Carrot"
handshake), Dissonance voice, room-event relay, TimeSync stream.

SYMPTOM: the game hangs at 18% loading into the dorm room, every time.

ROOT-CAUSE EVIDENCE (from the 2026 client's own Player.log, attempt
2026-11-08 21:43 UTC, server v7): a Newtonsoft JSON parse exception inside
TachyonClient.NetworkManager_OnClientConnectedCallback —
"unexpected character D at position 0" — then FailedToConnectToVoice (8719).

The approval Payload the server sends is the string:
    {"DR":"Carrot","KT":"<base64 RSA(SessionKeyB)>"}
(char index 2 of that string is 'D' — exactly the character the client chokes
on at position 0, i.e. the string the client RECONSTRUCTS starts two chars in
and is truncated.)

STATUS OF BUILDS:
- v7 (sha 807e45c0...): approval built per the 2025 fork layout in
  docs/ngo-fork-batch-and-approval.md. Client throws the 'D' exception above.
- v8 (sha 68e2523a..., CURRENT source in src/): Bob's hypothesis — the 2026
  ConnectionApprovedMessage.Deserialize consumes TWO extra bit-packed scalar
  values between NetworkTick and the Payload string vs the 2025 layout, so v8
  writes [bitpacked ownerClientId][bitpacked 0] there
  (NgoMessages.BuildApprovalBody). v8 ALSO FAILED on the real client
  (2026-11-10, still 18%). No client exception text from the v8 attempt has
  been captured yet — GET IT: it discriminates the layout precisely (see §5).

YOUR JOB: find the true 2026 ConnectionApprovedMessage wire layout and fix
BuildApprovalBody so the client's callback parses the payload cleanly; then
prove it on the real client (dorm loads past 18%).

5. HOW TO CRACK THE LAYOUT (fastest paths, in order)
--------------------------------------------------------------------------------
a) Read the v8 attempt's Player.log exception FIRST (Armin's PC, latest
   launch). Compare with v7's "D at position 0":
   - No JSON exception anymore, still hangs -> approval is FIXED; the blocker
     moved downstream (check server.log for the encryption marker flip
     0x11 -> 0x2A and what arrives after approval).
   - Exception char changed -> count how far into {"DR":"Carrot","KT":...}
     that char sits; the shift tells you exactly how many packed values the
     2026 reader consumes before/within the string. Adjust BuildApprovalBody.
   - Same 'D' at 0 -> v8's two values were consumed as something else
     entirely (e.g. a length+count pair); think again from the byte level
     using the approval-body hex line in server.log.
b) Decompile the 2026 client's ConnectionApprovedMessage.Deserialize
   (IL2CPP; type names are unobfuscated Unity.Netcode.* — the 2025 fork's was
   at 0x972F7D0; the patch-2026 notes/tools may help locate the 2026 one) and
   diff its read sequence field-by-field against BuildApprovalBody.
c) Ground-truth bytes: the server's [reqdump] log lines capture the client's
   own ConnectionRequest datagram hex; the client's writer is the same NGO
   stack as its reader — the request's field encodings (versions walk, then
   the AuthPayload byte[] framing) are proven-correct reference encodings.

PROVEN-CORRECT PARTS (do not re-litigate): LiteNetLib protocol 13 connect;
24-byte batch header (BatchCount @16) + XXHash64 (client accepts our
batches); per-message [packed index][packed size][body] framing; the fork
bit-packing (encoded = (value<<3)|numBytes, ZigZag signed); AuthPayload
decryption (VB self-test PASSES vs the real client; account in the token
matches AI=121); Dissonance framing (docs/dissonance-named-message-framing.md,
fork uses a 16-bit named type — do NOT switch to stock NGO's 64-bit hash on
the fork's word alone; NgoMessages already dual-parses both).
