# sf3-2025.json — provenance

**Source:** `../db/Watch_EnumValue_3.json` — a full capture of the real Rec Room
Watch store (storefront enum value 3), 3,326 items.

**Why authentic:**
- Item `AvailableAt` dates run 2021-09-03 → 2026-04-01 (right up to the June 2026
  Rec Room shutdown) — consistent with a genuine late-life API capture.
- Full native API shape per item: `GiftDrop` (with `AvatarItemDesc`,
  `AvatarItemId`, `AvatarItemInfo`, `ThumbnailImageName`, `ItemSetId`, …),
  `Prices` / `SubscriberPrices` with 133 distinct real token prices
  (not a generated rarity→price table), `AvailableAt`/`AvailableUntil`,
  `CanBeGifted`, `IsFeatured`, `NewUntil`.
- 2,830 of 3,306 items carry a real CDN `ThumbnailImageName`.
- Zero fabricated placeholder names (no "Classic Cap" / "Top Hat" style entries).

**Transformations applied (2026-10-01):**
1. De-duplicated by `PurchasableItemId` (20 true-duplicate pagination overlaps in
   the capture) → 3,306 items. First occurrence kept.
2. `NextUpdate` set to `2226-06-14T00:12:20.1324853Z` (far-future sentinel, same
   convention as the generated storefronts). The capture's `2026-08-09` is stale
   and trips the client's "New items in: time has passed!" bug.
3. Everything else — ids, names, prices, subscriber prices, discount percent
   (`SubscriberDiscountPercent: 10`) — served byte-identical to the capture.

**Replaced (2026-10-01):** the previous `sf3-2025.json` was a merged
"franken-file": 1,957 cherry-picked capture items mixed with 1,534 generated
items whose prices came from an invented rarity→price table and whose ids
(starting at 12132) matched nothing. Backup of the replaced file:
`/tmp/sf3-2025.franken-backup.json` (ephemeral).

**Served to:** builds newer than `LEGACY_CLIENT_BUILD` (20230414) requesting
storefront 3 — i.e. the July 2025 client. Older builds get the generated
`sf3.json` (unchanged).

**Extraction method (reproducible):** the July 2025 client binary
(`GameAssembly.dll`, `global-metadata.dat`) is string-encrypted — item names
cannot be mined from it. The storefront catalog is server-driven by design; the
capture above is the authoritative source. Verified 2026-10-01 by diffing the
served file against the capture.

**Sale-data strip (2026-10-05, re-applied and committed 2026-10-08):**
4. All 6,612 `StorefrontSaleData` entries removed from every `Prices` /
   `SubscriberPrices` entry. The capture's sale metadata was a stale 80%-off
   sale (`SaleStartDate: 2026-03-30`, no end date) from the real Rec Room API;
   serving it makes the client show every item at 80% discount. With the key
   absent the client treats items as not on sale. DO NOT reintroduce sale
   metadata without verifying live — a redeploy from an unstripped file
   reverts this (happened 2026-10-07).
